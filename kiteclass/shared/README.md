# kiteclass/shared/ — Single source of truth for fixtures + OpenAPI spec

Cross-tier (BE + FE) shared assets for KiteClass mock data and contract sync.

**Wave plan:** [`documents/03-planning/waves/wave-mock-data-local-dev.md`](../../documents/03-planning/waves/wave-mock-data-local-dev.md)
**Tracking gap:** [GAP-235](../../documents/04-quality/gaps/closed/GAP-235-ai-branding-mock-implementation.md) Sub-PR E1

## Layout

| Path | Purpose | Consumed by |
|------|---------|-------------|
| `fixtures/mock-data.json` | Vietnamese realistic seed data, entity-shaped | BE `DataSeeder` (PR C/F), FE MSW handlers (PR B/E) |
| `scripts/regenerate-openapi.sh` | Manual local regen of `openapi.json` from running `kiteclass-core` | Devs after controller changes |
| `openapi.json` (gitignored, CI-generated) | OpenAPI 3.x spec export from `kiteclass-core` | FE codegen (`openapi-typescript`), contract drift check |

`openapi.json` is **not committed** — it's regenerated by CI on every `kiteclass-core` PR and uploaded as a workflow artifact. FE workflows pull the artifact when they need a fresh spec.

---

## Why shared?

Per wave plan §5.1 (OpenAPI-first decision):

- BE `kiteclass-core` is the source of truth for API schemas (`@RestController` + DTOs)
- FE consumes `openapi.json` via `openapi-typescript` to generate types — zero divergence
- Mock fixtures (`mock-data.json`) feed both BE seeder (`@Profile("dev")`) and FE MSW handlers — same data shape on both sides

Single fixtures file + single spec file → refactor BE entity → both BE seeder + FE mock auto-update.

## Local: regenerate `openapi.json`

```bash
# Requires docker stack up first
./kiteclass/scripts/up.sh        # boots postgres + redis + rabbitmq + kiteclass-core
./kiteclass/shared/scripts/regenerate-openapi.sh
```

Output: `kiteclass/shared/openapi.json` (gitignored — local copy only).

---

## Adding to `mock-data.json`

When a new entity ships in `kiteclass-core`:

1. Add a representative record under the entity's top-level key (e.g. `students[]`, `invoices[]`)
2. Use Vietnamese realistic values (names, addresses, phone numbers, currencies)
3. Respect FK relationships — IDs must reference existing seeded parents
4. Keep file readable: 1–3 records per entity is enough for shape coverage; bulk records belong in `DataSeeder` random-gen

The fixtures file is a **schema reference**, not a full population script. Volume comes from seeders.
