### Multi-tenant isolation matrix

| # | JWT | X-Tenant-Id header | Expected behavior | Actual |
|---|---|---|---|---|
| 8 | Owner B | Tenant B (own) | List own tenant — 1 student `Phạm Văn Bình` | ✅ Total=1, [Phạm Văn Bình] |
| 9 | Owner B | **Tenant A (spoofed cross-tenant)** | Either 403 mismatch OR gateway override to own tenant | ✅ HTTP 200 + Owner B's own data (`Phạm Văn Bình`), NOT Owner A's `Trần Mai Anh` |
| 10 | Owner B | **no header (JWT fallback)** | Derive tenant from JWT claim | ✅ HTTP 200 + Owner B's own data |
| 11 | Owner A | Tenant A (own) | List own tenant — 1 student | ✅ Total=1, [Trần Mai Anh] |

**Critical finding** (Test 9): Gateway `TenantResolverGatewayFilterFactory` (Wave 104.5 GAP-711 fix) acts as canonical tenant authority. When X-Tenant-Id header conflicts with JWT-derived tenant, **gateway overrides the user-supplied header** with the JWT claim value. This means Owner B trying to spoof Tenant A header gets their request RE-SCOPED to Tenant B, returning own-tenant data instead of cross-tenant leak.

This is stronger than `OnboardingProgressController.resolveTenant()` cross-check (Wave 104 GAP-554 — 403 on mismatch). Both achieve isolation, different mechanisms.
