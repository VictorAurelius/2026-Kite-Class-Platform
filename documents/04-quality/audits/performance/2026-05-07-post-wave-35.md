## Verification — Wave 35 Closure Items

### ✅ GAP-392 N+1 fully closed

**Trước (Wave 34, broken):**
```java
// SlugAvailabilityService.isTaken() — full table scan EVERY keystroke
brandingJobRepository.findAll().stream()
    .map(j -> normalize(j.getOrganizationName()))
    .anyMatch(n -> n.equals(slug));
```

**Sau (Wave 35, fixed — verified):**
```java
// SlugAvailabilityService.java:94
return brandingJobRepository.existsByOrganizationNameLowercased(normalized);

// BrandingJobRepository.java:59-61
@Query("SELECT (COUNT(j) > 0) FROM BrandingJob j WHERE LOWER(j.organizationName) = :slug")
boolean existsByOrganizationNameLowercased(@Param("slug") String slug);
```

Regression test guard `SlugAvailabilityServiceTest:108` xác nhận `verify(jobRepo, never()).findAll()` — không thể quay lại N+1 anti-pattern.

**Semantic note** (đã ghi rõ trong javadoc): query so sánh `LOWER(organization_name) == slug` thay vì áp dụng full normalize (hyphenation + strip non-alphanumeric). Edge case `"Acme Corp" → "acme-corp"` không match nữa — đã track follow-up về stored `slug_normalised` column.

### ✅ V31 indexes verified

`kitehub/kitehub-subscription/src/main/resources/db/migration/V31__index_branding_job_organization_name_and_status.sql`:

```sql
CREATE INDEX IF NOT EXISTS idx_branding_job_org_name_lower
    ON branding_jobs (LOWER(organization_name));

CREATE INDEX IF NOT EXISTS idx_branding_job_status
    ON branding_jobs (status);
```

- Functional index trên `LOWER(organization_name)` → query `WHERE LOWER(...) = :slug` chuyển từ seq-scan O(n) sang index-scan O(log n).
- Btree index trên `status` → đóng P1 #4 (poll loop missing index) từ prev audit. Selectivity OK vì admin queue chủ yếu filter QUEUED/PROCESSING (cardinality nhỏ).
- `IF NOT EXISTS` an toàn re-run (idempotent).

**Limitations:** không có `EXPLAIN ANALYZE` trên dev DB → không xác nhận planner thực sự dùng index. Theo lý thuyết Postgres functional index sẽ kick in cho identical expression `LOWER(organization_name) = ?`.
