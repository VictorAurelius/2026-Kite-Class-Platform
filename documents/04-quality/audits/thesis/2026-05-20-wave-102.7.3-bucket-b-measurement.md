## Finding-by-finding resolution

### P2-01 — P95 API latency probe endpoint clarification

**Original wording (chapter-4-deployment-results.md line 213):**
> | P95 API latency | <500 ms | Sơ bộ 280-350 ms — đo từ public web check tới `/actuator/health` qua ALB, baseline beta thấp |

**Problem:** `/actuator/health` là Spring Boot probe endpoint trả về JSON `{"status":"UP"}` đơn giản — KHÔNG đại diện cho controller path nghiệp vụ thực tế (DB lookup + tenant context resolve + business logic). Số `280-350 ms` không phản ánh production-grade latency mà committee/GVPB sẽ hỏi khi đọc tới KPI table này.

**Fix:**
- Methodology block thêm trước KPI table giải thích rõ:
  - Tool: web-probe từ TP.HCM
  - N: 5 lượt (small sample, sẽ tăng khi cohort beta active)
  - Path: TP.HCM → ALB → `/actuator/health`
  - **Caveat explicit:** "KHÔNG đại diện cho controller path nghiệp vụ"
  - Roadmap: thay bằng production endpoint sampling khi cohort beta active
- Bảng KPI row reframe: `Sơ bộ 280-350 ms — đo từ public web check tới /actuator/health qua ALB, baseline beta thấp` → `Probe-endpoint sample 280-350 ms (xem phương pháp đo lường ở trên)`

**Why fix works:**
- Reader (GVPB/Defense committee) đọc bảng → trỏ ngay lên methodology block → hiểu rõ scope limitation
- Tránh được câu hỏi "Sao p95 lại thấp vậy với production?" — vì đã chủ động declare đây là probe endpoint
- Per S5 (Measurement methodology mandate): tool + N + date + env declared

### P2-02 — Uptime SLO estimate vs measurement

**Original wording (chapter-4-deployment-results.md line 212):**
> | Uptime SLO | ≥99,0% | Sơ bộ ≥99,2% — ước tính theo public AWS SLA cho EC2 t3.micro ap-southeast-1 (Multi-AZ disabled); kiểm chứng bằng CloudWatch availability metric |

**Problem:** Wording vừa nói "ước tính" vừa nói "kiểm chứng bằng CloudWatch" — mâu thuẫn implicit. Reality: chưa có CloudWatch availability metric đủ dữ liệu (cohort beta chưa active >30 ngày). Số `≥99,2%` là pure estimate theo public AWS SLA documentation, không phải measurement.

**Fix:**
- Methodology block declare rõ:
  - **Type:** *ước tính* (NOT measurement)
  - Source: public AWS SLA cho EC2 t3.micro `ap-southeast-1` single-AZ
  - **Caveat explicit:** "KHÔNG phải đo thực từ CloudWatch availability metric"
  - Reason: "cohort beta chưa đủ dữ liệu khoảng thời gian tối thiểu để baseline"
  - Roadmap: cập nhật khi có ≥30 ngày uptime data
- Bảng KPI row reframe: `Sơ bộ ≥99,2% — ước tính theo public AWS SLA ... kiểm chứng bằng CloudWatch availability metric` → `Ước tính ≥99,2% (theo SLA — xem phương pháp đo lường ở trên)`

**Why fix works:**
- Loại bỏ mâu thuẫn "ước tính + kiểm chứng" — chỉ là ước tính, period
- Honest acknowledgment "chưa có dữ liệu measurement" — committee respect honesty over false precision
- Per S5: type (ước tính vs measurement), source, caveat, roadmap declared

### P2-09 — Lighthouse Performance single measurement disclaimer

**Original wording (chapter-4-deployment-results.md line 214):**
> | Lighthouse Performance (landing) | ≥85 | Sơ bộ 92/100 — Lighthouse audit kitehub.me mobile profile |

**Problem:** Single measurement không có date / env / throttling profile / N-sample disclaimer. Reader không biết:
- Đo khi nào? (today vs 1 tháng trước)
- Tool version nào? (Lighthouse v9 vs v11 results khác nhau)
- Throttling profile gì? (mobile 4G simulated vs desktop no-throttle ra điểm khác)
- Lặp bao nhiêu lần? (single shot có variance lớn, cần median của N≥5)

**Fix:**
- Methodology block declare rõ:
  - Tool: Chrome DevTools Lighthouse audit
  - Profile: mobile
  - URL: `https://kitehub.me`
  - Date: 2026-05-15 (Wave 85 ship date approx — verified per audit context)
  - Throttling: default
  - **Caveat explicit:** "Chưa lặp N≥5 để baseline reproducibility — cần lặp + median khi định kỳ benchmark"
- Bảng KPI row reframe: `Sơ bộ 92/100 — Lighthouse audit kitehub.me mobile profile` → `Single audit 92/100 (xem phương pháp đo lường ở trên)`

**Why fix works:**
- Per S5: tool / date / env / profile declared
- Honest "chưa N≥5" disclaimer — committee biết single measurement có variance, không trust như baseline measurement
- Roadmap "lặp + median khi định kỳ benchmark" cho thấy author hiểu reproducibility requirement

### F-B4-01 — Cross-KPI methodology vague

**Original wording:** Toàn bảng `## 4.3.4 Kết quả đo giai đoạn beta (sơ bộ)` chỉ có 1 dòng intro `Các KPI System Health đã có số liệu sơ bộ thu thập được từ public probes; các KPI Acquisition + Engagement cần cohort tenant đủ lớn nên sẽ cập nhật trước defense:` — không phân biệt rõ estimate vs measurement vs sample cho từng KPI.

**Problem:** "sơ bộ" áp dụng chung cho cả 3 KPI System Health nhưng thực ra:
- Uptime SLO = pure estimate (public SLA)
- P95 API latency = probe-endpoint sample (5 lượt web-probe)
- Lighthouse Performance = single measurement (1 audit run)

3 types khác nhau bị gộp chung dưới label "sơ bộ" → reader không phân biệt được mức confidence khác nhau.

**Fix:** Methodology block §4.3.4 phân loại rõ 3 types qua 3 bullets riêng — mỗi bullet declare type (ước tính / probe-endpoint sample / single measurement), tool, N, date, env, caveat, roadmap.

**Why fix works:**
- 3 KPI mỗi loại có context riêng biệt
- Tổng kết Acquisition + Engagement KPI status riêng (cohort dependent — thêm bullet cuối)
- Reader trace từ bảng KPI table → methodology block → hiểu rõ scope từng cell

## Reproducibility note — how to re-measure each KPI properly

Khi cần re-baseline 3 KPI System Health với proper N + date + env cho next iteration (Wave 102.8+ hoặc post-cohort-active):

### Uptime SLO (Type: measurement, target N≥30 days)

```bash
# Pre-requisites: CloudWatch metric SystemFailureCount + EC2 instance state metric trên 30+ ngày
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 \
  --metric-name StatusCheckFailed \
  --dimensions Name=InstanceId,Value=<KH-BACKEND-EC2-ID> \
  --start-time 2026-04-20T00:00:00Z \
  --end-time 2026-05-20T00:00:00Z \
  --period 86400 \
  --statistics Sum
# Compute: (1 - failures/total_seconds) × 100
# Target: ≥99,0% (BR-INFRA-UPTIME-SLO per release-1-plan-2026.md)
```

### P95 API latency (Type: production endpoint sampling, target N=500 requests)

```bash
# Replace probe endpoint với production controller path
# Sample: POST /api/v1/auth/login (controller path đi DB lookup)
# Tool: JMeter 5.5 OR k6
# Profile: VN mobile 4G throttling
# Date: log measurement date in artifact
# N: 500 requests, p95 calculation
# Env: production endpoint api.kitehub.me from Vietnam mobile 4G
```

### Lighthouse Performance (Type: single audit → median of N≥5)

```bash
# Repeat audit N≥5 lần khác giờ trong ngày (var: network condition)
for i in 1 2 3 4 5; do
  lighthouse https://kitehub.me \
    --preset=mobile \
    --output=json \
    --output-path=./lh-run-$i.json \
    --quiet
  sleep 60  # space out để tránh CDN cache effect
done
# Compute median across 5 runs cho stable baseline
# Target: ≥85 Performance score
```
