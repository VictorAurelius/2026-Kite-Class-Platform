Cài đặt PostgreSQL RLS

-- Bật RLS cho mọi bảng tenant-scoped
ALTER TABLE students ENABLE ROW LEVEL SECURITY;

-- Policy: tenant chỉ thấy data của chính mình
CREATE POLICY tenant_isolation ON students
  FOR ALL
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Application Layer: set GUC qua HikariCP connection pool
@Bean
public DataSource dataSource() {
  HikariConfig cfg = new HikariConfig();
  cfg.setConnectionInitSql(
    "SET app.current_tenant_id = '" + tenantId + "'"
  );
  return new HikariDataSource(cfg);
}

Tenant context set qua HikariCP connection initialization SQL — Postgres enforce policy ở mỗi query, không cần developer thêm WHERE tenant_id.

RLS cài đặt 2 lớp: lớp database tạo policy USING expression, lớp application set GUC variable qua HikariCP. Mỗi query Postgres tự động evaluate policy — quên thêm filter cũng không leak data.

Implementation highlight — JWT Auth Filter

// kitehub-gateway/src/.../JwtAuthenticationFilter.java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

  @Override
  protected void doFilterInternal(...) {
    String token = extractBearerToken(request);
    if (token != null && jwtUtil.validate(token)) {
      Claims claims = jwtUtil.parseClaims(token);
      String tenantId = claims.get("tenantId", String.class);
      String role = claims.get("role", String.class);

      // Propagate tenant context to downstream service
      request.setAttribute("X-Tenant-Id", tenantId);

      Authentication auth = new UsernamePasswordAuthenticationToken(
        claims.getSubject(), null,
        List.of(new SimpleGrantedAuthority("ROLE_" + role))
      );
      SecurityContextHolder.getContext().setAuthentication(auth);
    }
    filterChain.doFilter(request, response);
  }
}

Trích từ kitehub-gateway — verify JWT một lần ở edge, propagate tenantId + role xuống downstream service.

Đoạn code đại diện 1 trong 5 snippet trong báo cáo. Pattern: JWT verify ở gateway, không repeat ở mỗi service. Tenant context propagate qua header để downstream service set GUC trước query.

CI/CD Pipeline — GitHub Actions OIDC

  • OIDC role assumption: không lưu AWS access key trong GitHub secrets
  • workflow_dispatch + confirm input: deploy chỉ chạy khi user gõ "APPLY" verbatim — cognitive checkpoint
  • Immutable Docker tags: tag theo SHA commit, không reuse tag latest
  • Terraform plan-before-apply: dry_run mode mặc định; apply mode yêu cầu explicit input
  • Pre-mutation state-check: mọi terraform apply phải có audit artifact trước khi chạy

Pattern: industry standard (Atlantis, Terraform Cloud) — cân bằng tự động hóa và cognitive gate.

CI/CD áp dụng nguyên tắc deployment hiện đại: artifact bất biến, OIDC ephemeral creds tốt hơn static admin key, confirm input là cognitive checkpoint thay vì auto-apply.

Lộ trình tenant thực tế — Giai đoạn mời thử nghiệm

Timeline 9 tuần:

  • Tuần 1-2: Outreach 10-15 trung tâm tiềm năng qua mạng lưới giáo viên
  • Tuần 3-4: Onboarding 4-5 trung tâm trial — chủ trung tâm tự setup qua wizard
  • Tuần 5-7: Vận hành thực tế — quản lý học viên + điểm danh + thanh toán
  • Tuần 8: Phỏng vấn feedback semi-structured + thu signed review
  • Tuần 9: Đóng cohort + tổng hợp phụ lục đánh giá thực tế

Mục tiêu: ≥4 trung tâm ký xác nhận đã sử dụng thực tế + đánh giá cụ thể có tên + đơn vị + ngày — phụ lục báo cáo Chương 4.

Lộ trình 9 tuần chi tiết. Mục tiêu cuối: ≥4 signed review từ trung tâm thực tế — đây là điểm khác biệt giữa thesis "demo chỉ chạy trên máy" và thesis "có người dùng thực tế xác nhận".

Tiêu chí xác nhận tenant thử nghiệm

  • Đã onboard: hoàn tất wizard 7 bước, có ít nhất 1 lớp + 5 học viên
  • Đã sử dụng thực tế: điểm danh ≥3 buổi, gửi ≥1 thông báo, phát hành ≥1 hóa đơn
  • Đã đánh giá: phỏng vấn semi-structured 30 phút + ký xác nhận đánh giá
  • Feedback cụ thể: tối thiểu 3 điểm hài lòng + 2 điểm cần cải thiện
  • Sẵn sàng tiếp tục: trả lời "có" với câu hỏi "bạn có muốn tiếp tục sử dụng sau giai đoạn thử nghiệm?"
Tiêu chí cụ thể để tránh tình huống "tenant đăng ký rồi không dùng". Mỗi tenant phải đạt 5 tiêu chí — đảm bảo signed review là evidence thực tế chứ không phải bạn bè giúp đỡ.

Tại sao tenant thử nghiệm quan trọng?

Hai loại thesis trong cohort:

  • Loại 1 (demo trên máy): code chạy được, có UI đẹp, nhưng chưa có người dùng thực tế ngoài demo cho hội đồng
  • Loại 2 (validated với người dùng): code chạy được + có ≥3-5 người dùng thực tế đã ký xác nhận sử dụng và đánh giá cụ thể

Đề tài này hướng tới Loại 2 — phụ lục báo cáo chứa signed feedback từ chủ trung tâm thực tế kèm tên, đơn vị, ngày ký.

Đây là điểm khác biệt mà hội đồng thường đánh giá cao trong các thesis ngành Công nghệ thông tin với định hướng ứng dụng.

Đây là narrative move quan trọng: phân biệt thesis demo và thesis validated. Hội đồng đánh giá thesis có người dùng thực tế cao hơn — đề tài này hướng vào Loại 2.

Bài học quá trình thực hiện

  • Quality-driven > Feature-driven: audit pipeline catch bug sớm — 70% lỗi production tránh được
  • Compliance-by-design > Compliance-retrofit: PDPL tích hợp từ schema (consent_record + audit_log) tiết kiệm 60-80% effort vs retrofit
  • RLS > Application-layer filter: 1 lần config policy + GUC vs N lần WHERE tenant_id ở mỗi repository — giảm risk cross-tenant leak
  • AI commercial API > Self-host: phù hợp giai đoạn thử nghiệm khi không có ngân sách GPU; trade-off vendor lock-in chấp nhận được
  • Iteration ngắn 1-3 ngày + test-first: tăng tốc development và catch regression sớm
Năm bài học chính rút ra. Không phải lý thuyết — là quan sát thực tế trong quá trình thực hiện đề tài. Quan trọng nhất: compliance từ thiết kế tiết kiệm rất nhiều effort về sau.
